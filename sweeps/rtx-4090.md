# RTX 4090 24GB — contributor sweeps and studies

Contributor-authored deep dives for Qwen3.8-27B MTP on a single RTX 4090 24GB (Ada, sm_89).

### RTX 4090: Unsloth UD-Q4_K_XL Dynamic 3.0 at 196K / q4_0 KV — n-max 4 still wins overall
*by [@gilkman](https://github.com/gilkman)*

Existing 4090 rows in the main table are n-max 2 (Q4_K_M 47.7→76.3, UD-Q4_K_XL 36.1→74.8). This is a later stack on the same card class: Unsloth **UD-Q4_K_XL Dynamic 3.0**, **196608** context, **q4_0** K/V, llama.cpp **b10665** (`ca3d5a3e1`), Windows 11 build 26200 / CUDA, driver 616.56, stock 450 W. `-ngl 99` (all layers on this 27B), `--flash-attn on`, `--parallel 1` (`-np 1`), `GGML_CUDA_GRAPH_OPT=1`, thinking off. No mmproj. No `--spec-draft-p-min`.

| arm | n-max | overall median | overall mean | python | prose | bash | acceptance | VRAM used / free (MiB) |
|---|---:|---:|---:|---:|---:|---:|---|---|
| spec-off | — | 44.7 | 44.5 | 44.7 | 44.9 | 44.4 | — | 21788 / 2351 |
| MTP | 2 | 82.0 | 80.2 | 89.7 | **69.9** | 82.0 | 0.73–0.87 (0.80) | 23472 / 667 |
| MTP | **4** | **84.9** | **87.1** | **114.7** | 59.5 | 84.9 | 0.47–0.85 (0.64) | 23774 / 365 |

Per-prompt medians are probe.py's three-run median. Overall is probe.py's nine-run median/mean. Spec-off was almost flat across prompts (42.9–44.9).

**Findings:**

1. **n-max 4 beats n-max 2 on overall median** (84.9 vs 82.0, +3.5%; mean 87.1 vs 80.2, +8.6%) on this 24GB card. Rule 1's "24GB peaks at n-max 2" does not hold for the overall number here. The gain is the python/code prompt (89.7 → 114.7).
2. **Prose inverts.** mmap-vs-read is faster at n-max 2 (69.9 vs 59.5). Same code-up / prose-down shape as the A6000 and PRO 6000 notes. Daily on this box stays n-max 4 because mixed/code traffic dominates; a prose-heavy host would pick n-max 2.
3. **The baseline is the durable part vs the older 4090 XL row.** Spec-off 44.7 vs that row's 36.1 is a newer build + Dyn3 + 196K/q4, not an MTP claim. Flag gain vs our own spec-off is +90% at n-max 4 (44.7 → 84.9) and +84% at n-max 2 (44.7 → 82.0). Do not subtract against @rkvhtd's 36.1→74.8 pair.

**Method:** unchanged `probe.py` at commit `a4c3028`, three runs × three prompts, 400 tokens, thinking off, warmup discarded. Both arms `--parallel 1`; only `--spec-type draft-mtp --spec-draft-n-max N` changed (spec-off omitted those two flags). Requests included an `Authorization: Bearer` header because the server is started with `--api-key`; prompts, `RUNS`, `MAX_TOKENS`, and timing math were not changed. Acceptance from llama-server `/metrics` `spec_decode_num_accepted_tokens_total / spec_decode_num_draft_tokens_total` after that arm (range is per-position for n-max 4: 0.85 / 0.69 / 0.57 / 0.47). VRAM from `nvidia-smi` while that arm was loaded.

**Honest caveats:**

- Not headless. DWM, Chrome, and Steam helper were resident; GPU-Util was 0% and 37°C at the start of the n-max 4 arm (rule 7 still applies — a busy compositor can silently spill weights).
- 196K context, not the recipe's 131K default. The pairing is clean at 196K; it is not a 131K row.
- n-max 2 and n-max 4 were separate reloads of the same GGUF/flags, not a live n-max sweep without restart.
- No p-min sweep this pass (prior 4090 probe on this box at 81K/q8 found p-min 0.70 slower than ungated n-max 4).

### RTX 4090 on WSL2/Docker: ungated MTP wins on novel text, the n-gram chain wins on repetitive text, GRAPH_OPT does nothing, and the Shared Usage check stalls GPU copies under WSL2
*by [@coffeegrind123](https://github.com/coffeegrind123)*

Same box and server as the main-table WSL2/Docker row: orcarouter `Qwen3.8-27B-Uncensored-Q4_K_M.gguf`, 98,304 context, q8_0 K/V, official `server-cuda-b10689` image in Docker Desktop on WSL2, Windows 11 build 22621, driver 616.92, stock 450 W, `--parallel 1`. The server is a coding agent's backend, so it also runs `--cache-ram 2048`, `--cache-reuse 64` and `--ctx-checkpoints 4`; they are identical in every arm.

**Method (not `probe.py`).** Each arm is a full server recreate; only the spec flags change. Arms run in **interleaved rounds** (A B C / B C A / C A B), so a load drift lands on every arm equally. Round 1 is dropped (cold), and any round whose per-arm host load differs by more than 2.5x is dropped too; host load is stamped on every result. Each surviving round is 3 requests per arm per workload, compared with a permutation test. Two workloads:

- **novel**: a 1,053-token nonce-randomised prompt, 256 tokens out, prefix cache defeated. The pessimistic case for any n-gram drafter.
- **repetitive**: a 1,211-token file-rewrite task, 1,178 tokens out, where 98.8% of generated 12-token windows also occur in the prompt. The shape an agent editing files produces.

Decode is llama-server's own `timings.predicted_per_second`. Thinking was on (template default, `reasoning_effort` medium, 4096-token reasoning budget), not off as in `probe.py`, so reasoning tokens count toward the output. Novel runs at the server's temp 1.0; repetitive is greedy.

**1. p-min 0 against 0.40, n-max 4, `ngram-map-k,draft-mtp` held fixed.** Two independent sweeps, measured a few hours apart:

| sweep | novel | repetitive |
|---|---|---|
| phase 1 (n=6 per arm) | **+20.2%**, p=0.037 | +2.3%, p=0.62 |
| phase 2 (n=9 per arm) | **+14.4%**, p=0.042 | -3.9%, p=0.27 |

Positive on novel text in every usable round of both sweeps, no detectable effect on repetitive text. Rule 2 holds on this card: ungated is the right default.

**2. Depth, ungated.** n-max 5: +13.2% novel (p=0.07), +0.3% repetitive. n-max 6: +10.1% (p=0.14), +0.1%. Neither beats n-max 4 once the gate is off: going deeper than 4 buys nothing on this card at 96K either.

**3. The n-gram chain.** Against the chain at the same p-min, MTP alone:

| arm | novel | repetitive |
|---|---|---|
| `draft-mtp`, p-min 0 | +13.5%, p=0.08 (sign flips by round) | **-11.6%**, p=0.007 |
| `draft-mtp`, p-min 0.40 | +0.2% | **-16.1%**, p=0.002 |

This is the opposite of the 3090 finding that `ngram-map-k` chained with MTP loses (81.3 vs 90.9). Both can be true: on short novel text the n-gram table rarely hits and costs little, and on repetitive agent traffic it drafts whole spans MTP cannot (9.9 draft tokens per verify cycle against MTP's 3.98 ceiling at n-max 4). **Measure the chain on your own traffic, not on `probe.py`**: its three prompts are novel text, and on them the chain read 90.3 against 87.3 for MTP alone, inside the noise.

**4. `GGML_CUDA_GRAPH_OPT=1`**, the flag on the 196K section's run, never isolated there. Chain, n-max 4, p-min 0.40, on vs off: +3.0% novel (p=0.69), +4.7% repetitive (p=0.32), and the sign flips across round subsets. No measurable effect on this card. At b10689 the engine reads it as `atoi(env) == 1`, single GPU and CUDA graphs only.

**5. Under WSL2 the spill check is itself a contaminant.** The Windows 3090 section recommends `Get-Counter "\GPU Process Memory(pid_*)\Shared Usage"` as the residency test. Under Docker Desktop on WSL2 the server's GPU memory is held by `vmwp` (the VM worker), and **polling that counter stalls GPU to host copies** for its ~1 s sample window. Same server, same bench, polled every 2 s or not:

| | prompt-cache save | prefill tok/s | decode tok/s | wall per request |
|---|---|---|---|---|
| not polled | 0.52-0.64 s | 725-1584 | 62.8-69.2 | 5.0-5.6 s |
| polled every 2 s | 2.5 / 24.5 / 41.5 s | 487-1234 | 57.4-80.3 | 7.8-47.7 s |

The prompt-cache save is llama-server's `prompt_save` + `prompt_load`, a 198 MiB device-to-host state copy. MTP's per-step device-to-host traffic uses the same path, which is why decode spread widened. `nvidia-smi --query-gpu` polled every second did not do this. Read the counter once with the box idle, not during a run.

**The 586 MiB threshold does not carry over either.** Here `vmwp` Shared Usage reads ~1,000 MiB (1,002 idle-loaded, 1,047-1,091 during runs) at 2.6 GiB VRAM free, while decode sits at the community baseline in both arms (44.2 spec-off against the 196K section's 44.7). That is a healthy server; under WSL2 the counter carries more than the native-Windows staging it was calibrated on. Judge residency by decode against a known baseline, not by that number.

**Honest caveats:**

- Third-party uncensored quant, not unsloth. llama-server builds the MTP draft context from it and it drafts normally (acceptance 0.62, in the range of the unsloth rows), but it is one file, one card.
- Not headless: an idle Windows desktop held 913 MiB. Other agent sessions shared the host CPU; phase 2's round 2 was dropped by rule when one arm ran at host load 11.5 against 3.8.
- Speedups on novel text are relative to a gated p-min 0.40 production config, not to spec-off. The spec-off pairing is the main-table row.
