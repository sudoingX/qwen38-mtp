# RTX 3090 — contributor sweeps and studies

Contributor-authored deep dives for Qwen3.8-27B MTP, moved verbatim from the main README. Each section carries its author and original PR. Add yours via a PR to this file, row and footnote go in the main [community table](../README.md#community-numbers).

### RTX 3090 24GB: the KV cache is a third tuning knob (q4_0 vs turbo3, both MTP-on)
*by [@lsunay](https://x.com/lsunay1), PR #19*

Data: [@lsunay](https://x.com/lsunay1), Hermes agent on PC-18.

Same host, same quant (unsloth Q4_K_M), same spec flags on both arms: `--spec-type draft-mtp --spec-draft-n-max 3 --spec-draft-p-min 0.75 --spec-default`, `-np 1`, `-fa on`. Only the KV cache and the llama.cpp build differ — this is a cache A/B, not a spec-on/off A/B, and both arms are MTP-on.

| arm | KV cache | Context | llama.cpp build | Method | Decode | Acceptance |
|---|---|---|---|---|---|---|
| baseline | q4_0 | 185K | mtp-clean fork (llama27b-mtp:cuda) | live agent traffic, 14 turns (100–2700 tok) | **37.2 avg (29.3–45.4)** | 0.57 avg (0.47–0.69) |
| flag | **turbo3** | **200K (204800)** | turboquant v10465 (fca3093c9) | clean probe, 3×400 tok, medians of 3 | **54.2 avg (48.06–58.34)** | 0.64–0.84 (avg ~0.76) |

**+47% decode** on the same card with MTP active on both sides (37.2 → 54.2 avg; 38.2 → 56.2 median), and the acceptance band actually *rises* (0.57 → 0.64–0.84) — the faster verification pass leaves less draft-verify pressure per round. VRAM: 23.0 GB (q4_0, 185K) vs 23.3 GB (turbo3, 200K (204800)) of 24.6 GB.

Honest caveats, in order of size:

1. **Confounded build.** The two arms run different llama.cpp builds (an older `mtp-clean` fork vs turboquant v10465, ~2 months newer upstream). Part of the +47% is almost certainly the newer build's improved CUDA kernels, not the KV cache alone. A clean test would run both cache types on the same build; that was not possible here because the production `mtp-clean` image predates `--spec-default` and the turboquant image is the only one with turbo3.
2. **262K does not fit.** The turbo3 arm was planned at 262K (the repo's standard window) but the container failed to load the model at that size on 24 GB; 200K (204800) was the working ceiling. The q4_0 arm's 185K is its own working ceiling at `--cache-ram 10384`.
3. **Arm methods differ.** The baseline arm is live Hermes agent traffic (thinking on, real tool-call turns, 100–2700 output tokens) — realistic but noisier. The flag arm is a clean 3×400-token probe — controlled but short, which per the length rule underestimates the flag arm's advantage (spec scales with generation length).

What this section adds:

- **The KV cache type is a hidden third knob.** The community rules so far cover n-max and p-min; on a fully packed 24 GB card, q4_0 → turbo3 at n-max 3 is another large delta with the spec head already engaged.
- **Turbo3 + MTP + 204K fits a 24 GB card at ~95% VRAM** — the A6000 row shows 256K q8_0 at 40 GB; this is the 24 GB equivalent.
- **Acceptance rising under a faster serve is plausible**: verification gets cheaper, so the gate (p-min 0.75) passes more drafts. Treat as an observation, not a law.


### RTX 3090 24GB: two quants on one card, and two things that do nothing
*by [@dcrey7](https://github.com/dcrey7), PR #36*

Both rows above are the same machine, same build, same afternoon, so the pair
isolates the quant. The overclock (memory +1200, core +180, 430 W) is on for
every number here.

| quant | size | baseline | MTP n=2 | gain | acceptance |
|---|---:|---:|---:|---:|---:|
| unsloth UD-Q2_K_XL | 10.7 GB | 52.4 | 85.6 | +63% | 0.76 |
| unsloth UD-Q4_K_XL | 17.9 GB | 43.9 | 79.6 | +81% | 0.78 |

**The quant moves the baseline more than the flag choice does.** Going from the
17.9 GB file to the 10.7 GB one lifts the unassisted floor 43.9 -> 52.4, which
is most of the distance between this card and the other 3090 rows here. Worth
knowing before comparing baselines across rows: a row's quant size sets its
floor, so `Q4_K_M` rows and `UD-Q2_K_XL` rows are not measuring the same thing.

**The overclock is worth about +6.5%, not more.** On the matched Q4 file this
card baselines 43.9 against 41.3 on @hauntedhost's stock b10450 3090. I mention
the size because I nearly reported the overclock as a +27% effect by comparing
my Q2 baseline to their Q4 baseline, which is not a like-for-like comparison.

**`-fa 1` is already on, so adding it changes nothing.** `--flash-attn`
defaults to `auto` and auto resolves to on for this path. The proof is VRAM,
not speed: baseline and `-fa on` load 16338 and 16340 MiB, while `-fa off`
loads 23782 MiB, 7.4 GB more, because the unfused path materialises the
attention buffers. Anyone adding the flag expecting a gain will measure noise.

**`--spec-type draft-mtp,ngram-mod` segfaults here.** It dies mid-generation in
`server_context_impl::update_slots()`, reproducibly, on the third prompt. The
GMK EVO-X2 row calls that combination unstable; on this box it is a crash. The
same run also shows the repetition artifact that row warns about: with
ngram-mod the code prompt's three passes were 111.1 cold, then 124.4 and 122.5
warm, against 112.7 for MTP alone. `probe.py` sends each prompt three times, so
n-gram scores its own cache on runs two and three. `ngram-cache` and
`ngram-map-k` both ran clean and both lost (81.9 and 81.3 overall against 90.9
for MTP alone at n-max 4).

**Nothing else moved it.** Tested and rejected on this card, all against a
90 +/- 1 overall baseline at n-max 4: depths 3, 5 and 6; p-min 0.0 and 0.4;
KV cache q8_0 and q4_0; draft-model KV q8_0 (best code number of anything I
ran, 117.5, but worse overall); ubatch 256 and 1024. Power sweep from 250 W to
480 W: 390 W and 430 W are within noise of each other overall, 480 W is +6%,
and efficiency peaks around 300 W.

**A note on your overall column.** It is the median of nine runs, which on this
rig lands on the bash prompt, and that prompt moves about ±8 tok/s between
otherwise identical passes. I had a prose figure shift 5 tok/s and an
acceptance figure shift 0.04 between single passes, enough to reverse a
conclusion I had already written down. Every number in my rows is the median of
three complete probe passes rather than one.


### RTX 3080 10GB: the flag's own footprint is the context ceiling, and Windows hides the spill
*by [@ntindle](https://github.com/ntindle), PR #48*

The smallest-VRAM card in the merged table, and the only one holding the weights
*fully resident* under 12 GB — the 8 GB and 12 GB laptop rows proposed in #45
and #46 are smaller cards but run deliberately partial-offloaded, which turns
out to be the distinction the whole section is about (see 6). One RTX 3080 10 GB
(GA102, SM86), Ryzen 9 7900X, 32 GB DDR5, Windows 11, llama.cpp b10435
(`9e40df63b`), unsloth UD-IQ2_XXS (8.39 GiB), q8_0 KV, `--parallel 1`, thinking
off, `probe.py` unchanged at `70a699e`. Every number is the median of three
complete passes, per the note above — it changed my n-max winner, see below.

Small enough that both interesting effects here are about memory rather than
speed, and both of them are invisible to the tool everyone checks.

**1. Getting the compositor off the GPU is worth more than the flag is.**

Before touching a spec flag: `dwm.exe` was holding **1,846 MiB** of this card
for two 1440p monitors. Moving both displays onto the 7900X's iGPU (disabling
the panel in Windows display settings releases it without unplugging anything)
took idle VRAM from 1,004 MiB to 179 MiB and made the card headless.

| state | idle VRAM | max offload that fits | baseline |
|---|---:|---|---:|
| displays on the 3080 | 1,004 MiB | `ngl 62` (of ~64) | 33.0 |
| displays on the iGPU, 3080 headless | 179 MiB | **`ngl 99`, every layer** | **44.8** |

Both rows are b10435 at 8K, so this is the offload level alone: **+36% baseline
with no flag involved.** The last two layers are worth more than they look,
because at `ngl 62` the shortfall is paid on every single token. On a 24 GB card
this is a rounding error; here it is the largest single lever, and it stacks
with MTP to 33.0 → 65.7, almost exactly 2×.

Dropping the desktop resolution later took idle VRAM from 179 MiB to **64 MiB**,
which did not change any baseline but did move the context ceiling a full step.
That is 2b.

**2. The MTP arm costs ~580 MiB, and that — not the baseline's fit — sets your
context ceiling.**

The flag arm loads a second draft context. On this card it wants ~580 MiB more
than spec-off. That is affordable at 16K and not at 32K, and the failure is
silent:

| ctx | baseline | with flag | gain | dedicated headroom | MTP shared host mem |
|---|---:|---:|---:|---:|---:|
| 8K | 44.8 | **65.7** (n2) | **+47%** | 580 MiB | 142 → 184 MiB |
| **16K** | 44.6 | **63.8** (n2) | **+43%** | 506 MiB | 274 → 316 MiB |
| 32K | 45.4 | 24.7 (n2) | **−46%** | 446 MiB | 950 → 992 MiB |

The baseline is flat at ~45 across all three, so nothing is wrong with the
context itself. Only the arm carrying the draft context inverts. WDDM caps the
process's *dedicated* allocation and quietly puts the overflow in host RAM
across PCIe rather than failing the load — rule 7 arriving through a different
door: not a shared desktop, but the flag's own working set.

The practical rule for a small card: **size your context against the spec-on
arm.** Tune context spec-off, then add the flag, and you land in the inverted
band with nothing to tell you.

**2b. The cliff is sharp enough that 115 MiB of desktop moves it a whole
context step.**

I measured 16K twice, a day apart, with identical flags and an identical build.
The only difference was how much of the card the Windows desktop was holding —
179 MiB in the first run, 64 MiB in the second after dropping the desktop
resolution:

| 16K, `n-max 3`, identical flags | desktop on the 3080 | tok/s | MTP shared host mem |
|---|---:|---:|---:|
| first run | 179 MiB | 25.8 | 586 MiB |
| after dropping resolution | 64 MiB | **62.9** | 394 MiB |

**115 MiB of desktop VRAM is worth 2.4× throughput here**, because it is the
115 MiB that decides whether the draft context is resident. There is no gradual
degradation to warn you — you are at 63 tok/s or you are at 26, and the
transition is roughly one browser window wide. If you are within ~200 MiB of
your card's limit, your benchmark is measuring your compositor.

**3. Acceptance cannot detect this, and reads slightly *better* in the broken
configuration.**

| config | tok/s | aggregate acceptance | range |
|---|---:|---:|---|
| 16K, n-max 2 (the good one) | **63.8** | 0.75 (4,804/6,444) | 0.47–0.92 |
| 32K, n-max 2 (the inverted one) | 24.7 | 0.73 (4,858/6,634) | 0.49–0.93 |

Same flag, same draft depth, 2.6× the throughput difference, and acceptance is
flat to two points across it. The draft head is doing its job in both; the
tokens just cost 2.6× as much to verify once the weights are partly across the
bus. This is the strongest form of rule 2's "acceptance is a vanity metric" I
have measured — and it agrees with @cmoro-deusto's power-cap sweep in
[rtx-5090.md](rtx-5090.md), which finds acceptance flat to a percentage point
while throughput in the same cells swings 25%. Two unrelated axes, same result:
acceptance tracks the draft head, not the machine.

**4. What does detect it on Windows.**

Rule 7 says to verify residency with `mem_info_gtt_used` "or your vendor's
equivalent". On Windows + NVIDIA there is no GTT counter, and **`nvidia-smi` is
blind to this** — it reported 500–580 MiB free in every row of the table above,
including the ones running at 40% speed. The equivalent is a WDDM perf counter:

```powershell
Get-Counter "\GPU Process Memory(pid_<server-pid>*)\Shared Usage"
```

Spec-off sits at ~110 MiB (normal pinned staging). A healthy spec-on arm is
~140–320 MiB. An inverted one is 586 MiB and up, and 950 MiB at 32K. That
counter, not `memory.free`, is the go/no-go on this platform.

**5. n-max sweep.** 8K and 16K, headless, full offload.

| n-max | 8K tok/s | 16K tok/s | acceptance (16K) |
|---|---:|---:|---:|
| off | 44.8 | 44.6 | — |
| **2** | **65.7** (+47%) | **63.8** (+43%) | 0.75 |
| 3 | 62.8 (+40%) | 62.9 (+41%) | 0.67 |
| 4 | 55.6 (+24%) | not run | — |

n-max 2 at both windows, consistent with rule 1 — a starved card peaks at the
shallowest draft, because deeper drafts cost VRAM this card does not have *on
top of* the usual rejection penalty. That second cost is visible in the shared
counter: at 16K, n-max 2 sits at 274 MiB and n-max 3 at 394 MiB, so on this card
the depth knob and the context knob are spending the same budget.

**6. Where this sits against the other small-VRAM rows, which all gain.**

Worth reconciling, because at first read this section looks like it contradicts
them. The 8 GB 5060 Laptop (#45) gains +74% and the 12 GB PRO 3000 Laptop (#46)
gains +104% — both running IQ4_XS with most layers *deliberately* on the CPU.
This card, at 32K, loses 46% for what looks like the same reason (weights not
resident). Both are true, and the distinction is which side of the boundary you
start on:

| starting point | what MTP does to it | why |
|---|---|---|
| already CPU-offloaded (8 GB, 12 GB rows) | **large gain** (+74%, +104%) | decode is already bandwidth-bound; drafting amortises the streaming you were paying anyway |
| fully resident, flag fits (this row, ≤16K) | **solid gain** (+43–47%) | ordinary speculative-decode win |
| fully resident, flag does *not* fit (this row, 32K) | **large loss** (−46%) | the flag's own working set is what evicts the weights |

The dangerous configuration is the third one, and it is dangerous precisely
because it is adjacent to the second. The partial-offload rigs cannot fall into
it — they are already past it, and MTP is the right call there unconditionally.

There is a practical corollary for anyone with a small card choosing a quant:
**drop the quant until the weights fit entirely, rather than running a larger
quant partially offloaded.** This card at IQ2_XXS fully resident runs 63.8; the
12 GB laptop at IQ4_XS partially offloaded runs 10.8. That is a 6× throughput
difference in favour of the smaller file, and it swamps any flag-level tuning on
either side. It is a real quality trade — IQ2_XXS is a 2-bit quant and I am not
claiming otherwise — but on a 10 GB card it is the decision that matters most,
and it gets made before you ever type `--spec-type`.

**This is the number the three-pass rule changed.** On single passes I measured
n-max 3 at 67.5 and n-max 2 at 64.9 and had already written down that this card
peaked at 3, against the trend of every other small-VRAM row. Three complete
passes reversed it: n-max 2 went 64.4/65.7/68.5 and n-max 3 went 62.3/64.8/62.8.
The single-pass gap was noise of the exact size @dcrey7 warns about two sections
up, and I would have published the wrong knob.

**7. Stale-server check.** @dcrey7's warning one section up — a killed but
unreaped `llama-server` keeps answering `/health`, so the next arm reports the
previous arm's numbers, and the tell is a VRAM figure that does not move between
arms that should differ. Two arms here look like that tell and are not: at 32K,
spec-on loads 9,794 MiB against spec-off's 9,711, a gap far smaller than the
+578 MiB the same flag costs at 16K. That is the cap being hit, not a stale
server — the overflow is in the shared counter (950 MiB vs 116), and each arm's
own log carries its own `draft acceptance` lines. The harness now refuses to
start an arm if anything answers `/health` on the port or if any `llama-server`
process is alive, which is the cheap way to never have to argue this.

Caveats, in order of size:

1. **16K is a small window** next to the 128K–262K rows in this table. It is
   what an 8.39 GiB quant plus a ~580 MiB draft context leaves on 10 GB, and the
   point of the row is the ceiling mechanism, not the window.
2. **IQ2_XXS is a 2-bit quant** and this row's baseline is not comparable to the
   Q4_K_M rows above — per @dcrey7's point, a row's quant size sets its floor.
   No quality evaluation was run here; this section is throughput only.
3. **n-max 4 was measured at 8K only** (55.6), and on one pass rather than
   three, so treat it as a screen showing direction. Every number in the main
   tables — both windows, baseline and n-max 2 and 3 — is a median of three
   complete passes.
4. **The 32K baseline (45.4) is a single pass.** Its three-pass siblings at 8K
   and 16K landed at 44.8 and 44.6, and the spec-on arm it is compared against
   is a three-pass number, so the −46% is not sensitive to it.
5. **`--spec-draft-p-min` was not swept.** Rule 2 says to sweep it rather than
   adopt it, and I did not, so this section says nothing about it. On a card
   where the constraint is VRAM rather than draft quality I would not expect it
   to move the ceiling, but that is a guess and not a measurement.
